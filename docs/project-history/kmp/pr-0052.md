Fixes #31.

## What it costs today

Every merge to main re-runs 17 jobs — roughly eight minutes, including the container jobs that need Neo4j, Valkey and NATS — against a working tree that was proved green minutes earlier. Measured on the v0.1.4 release merge:

```
merge commit  45ba56d  tree 0597267016...
PR head       3833fff  tree 0597267016...
identical
```

Different commit, **byte-identical tree**. The gates compile and test a tree.

The compute is the smallest part. Those container jobs fail intermittently (#30), so doubling the runs doubles the chance of a red check on a tree that was green minutes before — and every false red trains the reflex to re-run rather than read. That reflex is what lets a real regression through.

## What lands

A `tree-proof` job runs first on pushes to main: it resolves this commit's tree and looks for a successful run of this same workflow whose head commit carries the same tree. Every gate hangs off its answer.

**The rule is "skip when this tree was already proved", never "trust the pull request."** That distinction is the whole design and it is load bearing:

| situation | what happens |
|---|---|
| merge from an up-to-date branch | tree matches a green run → gates skipped |
| merge from an out-of-date branch | tree nobody tested → **full gate** |
| conflict resolved in the GitHub UI | tree nobody tested → **full gate** |
| direct push to main | tree nobody tested → **full gate** |
| API will not answer / no repo / unresolvable commit | **full gate** |

Pull requests are untouched — the proof step only runs on `push`, so `skip` is empty there and everything runs as before.

## Verified against this repository, as it stands right now

Main's tree today is `bc000d63`. PR #51's head tree was `b22845ba` — **different**, because that branch was cut before #50 landed. The check answers "run the gates", which is the correct answer: the tree main now carries was never tested as a whole.

That is the more interesting verification, honestly. It shows the skip is conservative in exactly the case the issue warns about, rather than only that it fires when convenient. The saving arrives on merges from an up-to-date branch, which is most of them.

## Not done here

A merge queue is the other shape, and probably the better long-term one — it tests the exact commit that will land, which makes the post-merge run redundant by construction rather than by comparison. It is also a repository-settings change with branch-protection implications, so it belongs in its own decision rather than riding along with a workflow edit.

`publish-distribution`, `plugin-package` and CodeQL's default-branch analysis are untouched: they do work that only makes sense post-merge.
