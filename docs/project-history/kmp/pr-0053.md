## Author's change description

Fixes #28.

## What happened

Write a compensating entry with `rel: "supersedes"` — the ordinary way to revert a decision — and the older entry kept appearing in `kernel_wake` and `kernel_ask` exactly like a live one. Nothing said it had been replaced.

The supersession was never lost: it sat on the relation, reachable through `kernel_inspect` on the older entry and by rewinding. But a reader who does neither can act on a decision that was already replaced, which is the one failure a memory with an append-only log should not have.

## What lands

`Proof` gains `superseded` — one line per replaced entry, naming what replaced it and why:

```json
"superseded": [
  {
    "ref": "project:sup:entry:decision:usar-redb",
    "superseded_by": "project:sup:entry:decision:usar-sqlite",
    "why": "dos hosts necesitan compartir el store"
  }
],
"conflicts": []
```

## Why not just reuse `conflicts`

That channel already exists, it already surfaces `contradicts`, and adding `supersedes` to `is_conflict()` would have been a one-line change. It would also have been wrong.

The two mean different things and a reader has to tell them apart:

- **`contradicts`** — these two disagree, and you should know. Both may still be live; the tension *is* the information.
- **`supersedes`** — this one replaced that one. No tension, a lifecycle. The older entry is history rather than advice.

Folding them together would make every revert read as an unresolved disagreement, and a reader would learn to discount the channel that is supposed to stop them acting on stale decisions.

## Verified end to end

A decision, then a compensating decision that supersedes it, driven through the real MCP server against a fresh store — the output above is that run, not a fixture. `conflicts` stays empty, which is the point.

Along the way it also exercised #14's fix (seeding a fresh about) and the strict writer's `read_context` requirement for a rich relation, both behaving as intended.

## Also
