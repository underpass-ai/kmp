## Author's change description

`cargo install kmp-mcp` does not work today, and no CI job would have fixed
that: the crates themselves were unpublishable.

- Internal dependencies carried a `path` and no `version`. cargo refuses to
  upload a crate whose siblings it cannot resolve on the registry.
- `kmp-proto` compiled the contract from `../../api/proto`, and `kmp-mcp`
  embedded its fixture responses from `../../../api/examples`. `cargo
  publish` packages only what lives inside the crate directory, so those
  crates build here and nowhere else.
- Most crates had no `license`, `description` or `readme`, which crates.io
  requires, and no crate said whether it was meant to be published at all.

## What this does

**Twelve crates become publishable**, in the order the release publishes
them:

```
kmp-plugin-api  kmp-domain  kmp-ports  kmp-observability  kmp-memory-api
kmp-adapter-embedded  kmp-application  kmp-embedded  kmp-proto
kmp-proto-mapping  kmp-viewer  kmp-mcp
```

That is the transitive closure of `kmp-mcp`. Everything else — the server,
its transport, the deployed adapters, every test crate — is now explicitly
`publish = false`, with a line saying why. Each published crate gets the
metadata crates.io needs and a README that says what it is for.

**The contract now lives twice, on purpose.** `crates/kmp-proto/proto` and
`crates/kmp-mcp/fixtures` are vendored copies of what `api/` authors.
Duplication buys publishability and costs drift, so
`scripts/ci/check-vendored-contract.sh` diffs them on every pull request —
the published adapter cannot quietly start answering with examples the
kernel no longer produces.

**`scripts/ci/publish-crates.sh`** owns the publish order, skips versions
already on the registry (so a release that fails halfway is resumed by
re-running the job, never by moving a tag), and waits out the new-crate rate
limit: crates.io allows a burst of five new names and then one every ten
minutes, and a first release introduces twelve of them. The job's timeout is
sized for that wait; later releases publish new *versions*, which is a much
looser limit and takes minutes.

**`scripts/ci/check-publish-chain.sh`** keeps that list describing the
workspace — publishable crates missing from the chain, chain entries that
are not publishable, dependencies published after their dependents, missing
version requirements — on pull requests, where a mistake is still free.
crates.io versions are immutable.

**`scripts/release.sh`** moves the workspace version, the internal pins and
the chart together (`version`), and tags only what already agrees
(`release`). The internal pins are the easy thing to forget and the
expensive thing to get wrong.

Also: `docs/release.md`, a `CHANGELOG.md`, and the install docs now lead
with `cargo install kmp-mcp`.
