## Author's change description

## The problem

ADR-011 accepted a single-writer store on a stated premise:

> Two Claude Code sessions on the same project is realistic but occasional.

That is false now, and not because people open more windows. The plugin installs into **two different hosts** — Claude Code and Codex CLI — and a developer using both has them open at once. Whichever starts first owns the memory; the other gets an error it cannot act on without closing the tool it was about to work in.

The outcome depends on start order: it works, then it does not, and the user changed nothing. For a memory product that is the most expensive failure shape there is, because the response is to stop relying on it. ADR-011 wrote its own trigger — "if concurrent sessions prove common" — and it has fired.

## Evidence

New spike in `docs/adr/spikes/e-concurrency-spike/`, spawning **real OS processes**, which ADR-009's single-process benchmark could not do:

| engine | processes that opened | events durably written |
| --- | --- | --- |
| redb 4.1.0 | 1 / 2 | 300 / 600 |
| SQLite (WAL) | **2 / 2** | **600 / 600** |

A SQLite reader alongside a live writer completed 31,843 consistent, monotonic snapshots without blocking it.

ADR-009's deciding criteria re-measured on this machine, because the originals are from different hardware and quoting them would be sloppy:

| engine | batched write (ev/s) | reopen (ms) | point reads (r/s) | size (MB) |
| --- | --- | --- | --- | --- |
| redb 4.1.0 | 88,427 | 1.93 | 4,028,475 | 64.3 |
| SQLite (WAL) | 61,594 | **0.18** | 781,421 | **26.1** |

## Why this is not a PR to redb, and not a port either

The obvious question — fix redb instead of replacing it — turns out to be already in progress, and that changes the arithmetic.

`cberner/redb` has three open PRs from 2026-08-14 (#1375, #1376, #1377, ~2,000 lines) adding a `MultiProcessDatabase` behind `experimental-multiprocess`. None merged. #1375 says of itself:

> **this type has no advantage over `Database` yet**. It is the first step of an incomplete feature [...] and then the actual point of the exercise — readers attaching to a database another process is writing, and handing the writer role between processes.

And the design notes say why that remainder is the hard part: readers can only be admitted once they can publish what they are reading, and on Windows a shared lock denies writes to the holder, so all coordination must move into separate lock files. That is SQLite's `-shm` WAL-index, rebuilt.

## Recommendation: wait, mitigate, re-decide

The ADR lays out three options and recommends **B — wait for redb, mitigate now** — with a scheduled re-decision.

Not because porting is wrong on the merits; the spike says it works. Because of what we would buy it with. The embedded edition's pitch is a single pure-Rust binary that runs anywhere. Spending a C toolchain, a store migration and the static musl/Windows story to solve a problem upstream is visibly working on — for a user base currently near zero — is the wrong currency at the wrong time.

The trigger for re-deciding is written down: the reader-attach work landing, or visibly stalling, or a user who is not us reporting this. Whichever is first. The numbers are already measured, so that decision is cheap.

## What this PR does not do

No code. No engine change. This is the decision and its evidence, in the form ADR-009 set: an ADR plus a reproducible spike kept out of the workspace.

The honest consequence is recorded as accepted: **two agent hosts still cannot share one memory**, and the docs have to say so rather than let a user discover it by start order.
