## The gap was narrower than the issue guessed

I filed this saying nothing was logged. That was wrong: **the file log already existed** — `embedded_log_dir()` and a rolling `kmp-mcp.log` per data directory, and last night's failure has 45 log lines around it.

What bypassed it were the two lines that matter. The startup outcome went through `eprintln!` and `std::process::exit(2)`, never through tracing. So the log recorded every tool call and nothing about whether the server came up.

```
2026-08-16T23:12:31 INFO embedded backend data dir resolved
2026-08-16T23:17:27 INFO embedded backend data dir resolved   <- the failure was in here
2026-08-16T23:19:26 INFO embedded backend data dir resolved
```

## What lands

**Both outcomes are recorded.** The failure with its reason; the success with backend, engine and version. The success line earns its place: a log holding only failures cannot tell *"it has never started"* from *"it started, and the failure in this file is older than that"*.

**`embedded_log_dir` falls back to the per-user state home** when the data directory will not resolve — that case is itself a startup failure, and it was the one guaranteed to leave nothing behind.

**`kmp-doctor` reads it back:**

```
Startup history
  FAIL  2026-08-17 00:53:38  embedded store at `...` uses the sqlite engine, which this binary…
        the most recent start failed — that is why the tools are missing,
        and the reason above is what the host swallowed.
```

and on a healthy one:

```
Startup history
  ok    2026-08-17 00:53:38  embedded backend, redb engine
```

## One thing worth confessing

My first version of that parser **silently produced nothing** — an f-string with escaped quotes inside a single-quoted shell heredoc, with `2>/dev/null` swallowing the SyntaxError. The doctor cheerfully reported "no startup lines yet" while staring at a log that had one.

A diagnostic that fails quietly is precisely the failure it exists to report. Rewritten without the escapes, and verified against both a failing and a succeeding store.

## Verified

Two real stores driven through the real binary: a good start and a store this binary cannot open. Each left its line; the doctor read both back.
