## `kmp-mcp share-memory`

The seven manual steps, as one command:

```
$ kmp-mcp share-memory
snapshot taken (the live store was not touched)
migrated: 22 events, 370 mutations
verified: 22 events, last sequence 22, on both engines

`~/.local/share/kmp/default` is now on the sqlite engine and two hosts can share it.
the original is kept at `~/.local/share/kmp/default-redb-before-share` — nothing was deleted
restart every agent host so it opens the new store
```

The three traps from the issue, handled:

- **The store is locked by the session asking for the migration.** It snapshots first — copying files is a read and does not need the single-writer lock.
- **Nothing verified the result.** Both stores must report the same event count and last sequence, checked *before* the swap. A migration that reports success and loses events would otherwise be found by a reader, later.
- **The swap order can leave two live stores or none.** The original is moved aside as `<dir>-redb-before-share`, kept exactly as it was, and the change is undone by moving it back. Nothing is ever deleted.

It refuses rather than guesses, in every direction: no engine in the binary (says how to get one, before touching anything), a leftover working directory, a store already on sqlite (a no-op that says so), a verification mismatch, an occupied destination name.

## The doctor offers it — and offers the right thing

It already detected the condition and printed advice that **would fail on the machine reading it**: a `migrate` command naming the locked store, assuming an engine the binary probably did not have.

It now reads its own version string first:

```
warn  another process holds this store (pid 3686519)
      ...
      share the store between hosts by moving it to the sqlite engine.

        kmp-mcp share-memory

      one command: snapshots the store (yours is locked, so it cannot be
      migrated in place), migrates, verifies the event log matches, keeps
      the original under a -redb-before-share name, and installs the result.
```

and, on a binary without the engine, leads with `cargo install kmp-mcp --features sqlite` instead.

## A Plugin section, for #44

```
Plugin
  warn  plugin files are 0.1.3, binary is 0.1.5
        these update separately and neither announces the other:
          binary:  cargo install kmp-mcp --force
          plugin:  /plugin update kmp@underpass   (then restart the session)
        a stale plugin still starts, because the launcher falls back to the
        binary on PATH — so fixes that live in the launcher, this doctor or
        the skills are the ones you are missing.
```

That last sentence is the part worth having. A stale plugin with a fresh binary keeps working **by luck**, so the engine updates silently while everything that lives in the plugin stays old — which is exactly backwards from what anyone would assume.

## Verified end to end

On a copy of a real store: 22 events, 370 mutations, verified equal on both engines, original kept, two hosts then answering `tools/list` with ten moves each, and a second run reporting `already shareable` without touching anything.

One thing the gate taught me: **migration runs one way.** My first gate built its redb fixture by migrating the sqlite store down, and got `migration from a sqlite store is not supported yet`. The fixture is now created the way any first session creates one.

## Gates

`quality-gate.sh` and `embedded-sqlite-gates.sh` green. The sqlite gate drives `share-memory` over a real store and asserts all of it: the engine changed, the output says it verified, the original is kept, and a rerun is a no-op.
