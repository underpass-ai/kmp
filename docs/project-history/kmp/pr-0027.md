## Author's change description

Use case 3 of the three, and the last before 0.1.4.

## The shape

There is no delete in KMP, deliberately: a memory that can be quietly edited is a memory nobody can trust as evidence later. Reverting is a **write** — a new entry saying what is true now, connected with `supersedes` (evidential) carrying *why* the earlier decision stopped holding and the evidence that showed it.

That already worked. What did not exist was anywhere saying so, or showing what it buys.

## `/kmp:revert` demonstrates rather than describes

After the compensating write it does two reads, and reports both:

1. `kernel_ask` — the current answer leads with the new state.
2. `kernel_rewind` to before the reversal — the old decision is **still there**, with the evidence it had.

*"The memory now says X. As of before, it said Y, and here is why that changed."* That is what an append-only log buys and it is invisible until someone shows it.

Verified on the demo memory:

```
1. compensating write: accepted = True | relation: ['supersedes']
2. rewind to before it: returns the store as it was, without the new decision
3. the superseded decision still carries superseded_by, with its why
```

## Written to refuse where refusing is right

- **Confirm the ref before writing.** Reverting the wrong entry is not undoable by a second revert; it adds a second wrong entry to a permanent record.
- **Ask for the why if the user has not given one.** A supersession without a reason is a deletion with extra steps, and it destroys the only thing keeping the old decision was for.
- **Never look for a delete.** If someone wants an entry to stop being *findable* rather than stop being *current* — a secret, a name that should not be there — that is a different operation with different consequences. The command says so and stops rather than improvising.

## The limit, stated rather than discovered

**A superseded entry is not yet flagged as superseded in `kernel_wake` or `kernel_ask` output.** The supersession lives on the relation: visible through `kernel_inspect` on the older entry, and by rewinding. A reader who does neither can still act on a decision that was replaced.

That is exactly why the command shows both states instead of trusting the reader to notice, and it is written into the command and the skill so nobody relies on a marking that is not there. Worth noting what *does* work: `contradicts` is surfaced — `kernel_ask` with `answer_policy: "show_conflicts"` on the demo returns the contradiction with its full rationale. Supersession is a lifecycle fact rather than a conflict, so it needs its own channel rather than being folded into that one.

Filed as a follow-up issue with the design.
