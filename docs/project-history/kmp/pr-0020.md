## What this adds

```
kmp-mcp migrate <old-dir> <new-dir> --engine sqlite
```

The migration was already a replay of the event log into a fresh store — the event log is the source of truth, projections are derived, and that is how a format bump has always worked. The one missing piece was a say in **which engine the destination gets**. `EmbeddedKernelStore::migrate_data_dir_to` (and `open_or_migrate_data_dir_to`) take a `StorageEngine`; the old names keep the default and stay as they were.

The receipt records both layouts:

```json
{"source_format":1,"destination_format":2,"events_migrated":2,"mutations_applied":22,...}
```

## Verified

**In the test suite** (`migration_converts_a_redb_store_into_a_sqlite_store`): a redb store with real history → SQLite. Receipt `1 → 2`; destination stamped `2` with only `kernel.sqlite3` in `store/`; source byte-identical before and after; a plain `open()` dispatches to SQLite and reads the full history; and the strong check — **bundles exported from source and destination are byte-identical**, because a bundle is the event log and knows no engine. Without the feature, asking for SQLite is refused by name before anything is created.

**End to end, against the published 0.1.3 binary:**

| Step | Result |
|---|---|
| Store written by **0.1.3 from crates.io** (redb, format 1) | 2 events |
| `kmp-mcp migrate … --engine sqlite` with this build | receipt `1 → 2`, 22 mutations rebuilt, only `kernel.sqlite3` in destination |
| **0.1.3 tries to open the SQLite store** | `format version 2, newer than this binary supports; upgrade the binary` — **and no empty `kernel.redb` created beside it**. This is what `FORMAT_VERSION = 2` is for, checked against the real old binary |
| **Two `kmp-mcp` processes at once** on the SQLite store | A opens and wakes; while A holds it, B opens, wakes, **sees the decision written in the redb era**, and writes with `accepted: true` |

That last row is Codex and Claude Code sharing memory.

## Not in this PR

Migrating **from** a SQLite source stays refused with the reason: WAL keeps committed data in a sidecar until checkpointed, so a naive file copy would silently drop the newest events. A consistent snapshot (`VACUUM INTO`) is its own piece of work.
