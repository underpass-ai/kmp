## Author's change description

Adds a plugin that makes KMP memory discoverable from both sides: the agent learns *when* to reach for it, and the human gets a way to find out why it is not answering.

## Why

Using KMP today means three manual steps — install a binary, copy an MCP registration into your host's config, and paste the context-recovery playbook into `CLAUDE.md` or `AGENTS.md`. The plugin does all three, and adds the part that did not exist: a diagnosis.

## Install

```
# Claude Code — native, brings the MCP server with it
/plugin marketplace add underpass-ai/kmp
/plugin install kmp@underpass

# Codex CLI — no plugin system, so a script does the wiring
bash scripts/mcp/install-kmp-plugin.sh --codex
```

## For the agent

The `kmp-memory` skill carries the operating doctrine, loaded when work continues something earlier or a decision worth remembering is reached:

- **recover before re-deriving** — `kernel_wake {about}` before reading files to rebuild context that may already be stored;
- **write decisions, constraints and outcomes — never transcripts**;
- **rich relations carry both `why` and `evidence`**, so a vague `related_to` is a bug rather than a shortcut;
- `UNKNOWN` from `kernel_ask` is a correct answer, not something to route around.

It defers to `tools/list` as the authority on the relation vocabulary, since that catalog is generated from the kernel's writer spec and moves with the kernel. The skill teaches the shape; the schema carries the truth.

## For the human

| Command | Does |
| --- | --- |
| `/kmp:doctor` | Diagnoses the setup end to end and names the one thing to fix |
| `/kmp:moves` | The ten moves and when to use each, read from the live surface when reachable |
| `/kmp:setup` | Installs and wires what is missing, then re-checks |

In Codex, `/kmp-doctor` and `/kmp-moves`.

The doctor exists because every failure looks identical from inside a session — the `kernel_*` tools are simply absent — while the causes are specific and separable: no binary, a `fixture` backend serving canned responses that look real, another session holding the store under the single-writer contract (ADR-011), or a session that started before the registration changed and is still carrying the old inventory. That last one cannot be fixed from inside the session, and the doctor says so.

**The doctor probes a scratch data directory, never the real one.** A diagnostic must not create a store as a side effect, and must not take the single-writer lock out from under a live session. Whether the real store is free is answered by looking at it (`fuser`/`lsof`), not by opening it. This was caught while testing — the first version created a `.kernel/` store just by running.

## Verification

Run against a real `kmp-mcp` build, not just inspected:

- tool surface probe returns all **10 moves** over real stdio JSON-RPC;
- ADR-012 data-directory resolution reports the right winner and why (`KMP_MCP_DATA_DIR` → project `.kernel/` → XDG fallback), exercised on all three;
- store-exists path reports format, size and lock state; `fixture` backend warns loudly;
- host-registration detection for Claude Code and Codex;
- confirmed the doctor leaves **no** store behind;
- installer `--dry-run` exercised; JSON manifests and both shell scripts syntax-checked.

Not verified: the end-to-end install inside a live Claude Code session (marketplace add → install → commands appear) and inside a live Codex session. The manifests follow the documented schema and the components sit at the plugin root as required, but the round trip has not been run.
