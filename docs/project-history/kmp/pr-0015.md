## Author's change description

## The bug

The plugin's MCP server never starts. `claude mcp list` on a machine with the sibling plugin installed the same way:

```
plugin:made:made: ./scripts/run-embedded-mcp.sh  - ✘ Failed to connect
  ENOENT: no such file or directory, posix_spawn './scripts/run-embedded-mcp.sh'
```

Both plugins declared the server the same way:

```json
{ "mcpServers": { "kernel-memory": { "cwd": ".", "command": "./scripts/run-embedded-mcp.sh" } } }
```

`cwd: "."` does not resolve to the plugin directory, so the host spawns the launcher relative to wherever the session started. The plugin installs cleanly, reports the right version, `claude plugin validate` passes and the skills load — the only thing that does not work is the memory, which is the reason to install it.

## The fix

```json
{ "mcpServers": { "kernel-memory": { "command": "${CLAUDE_PLUGIN_ROOT}/scripts/run-embedded-mcp.sh" } } }
```

`${CLAUDE_PLUGIN_ROOT}` is what the official marketplace plugins use for plugin-relative paths — none of them use a bare `cwd: "."` with a relative command. The `cwd` key is dropped entirely: `run-embedded-mcp.sh` already resolves its own location from `BASH_SOURCE`, so it does not care where it is invoked from.

## Verified

Invoked the installed launcher by absolute path from an unrelated working directory:

```
initialize: {'name': 'underpass-kmp-mcp', 'version': '0.1.3'}
tools: 10
```

`claude plugin validate plugins/kmp` passes.

## Note

This is the third variant of the same defect this week, all of them only reachable by installing the plugin as a user rather than reading it: the launcher pointed at a `bin/` that only exists in a release package (fixed in 0.1.3), the manifests were stamped at 0.1.0 forever (fixed in 0.1.3), and now the launcher is invoked from a path that does not exist. Each one leaves an install that looks correct and does nothing.

Same fix goes to the MADE plugin, which carries the identical declaration.
