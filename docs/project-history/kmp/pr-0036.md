## Author's change description

Fixes #34. Found while replicating ADR-018 in MADE, where the same defect showed up as a flaky two-process test.

## The claim that was wrong

ADR-018's spike recorded a real trap — `busy_timeout` must be armed **before** `journal_mode=WAL` — and then concluded:

> the fix is ordering, not retry logic

The ordering is right. The conclusion is not, and the implementation inherited it.

## What the switch actually does

| the other connection | switching to WAL |
| --- | --- |
| holds a **write** lock, database still in its default journal mode | fails **immediately** — `busy_timeout` is not consulted |
| holds a **read** lock, database still in its default journal mode | waits the whole timeout, then fails |
| holds any lock, database **already** in WAL | succeeds; the switch is a no-op |
| merely connected, no lock | succeeds |

So the window is narrower than the spike recorded and worse inside it: it exists only between a store file being created and its switch to WAL, and inside it an armed timeout buys nothing. Two hosts starting at the same instant against a data directory that has no store yet could lose one — which is exactly the state an operator is in right after migrating and pointing both hosts at the shared directory.

## The fix

`enter_wal` retries under the same bounded deadline every other wait already uses. The holder is another agent host doing precisely what this engine exists to allow, so waiting is the correct answer; the deadline keeps a genuinely stuck store reporting rather than hanging.

## Why the existing test could not catch it

`two_writers_one_store` stamps the data directory first, and stamping creates the store file and leaves it in WAL — so both writers take the no-op row of that table. The bug was invisible with the acceptance test for this very feature passing.

Two tests added:

- **`two_processes_creating_the_same_sqlite_store_at_once_both_get_in`** — same scenario one step earlier: keep the stamp, clear the store file, let both writers race to create it.
- **`an_open_waits_out_a_conversion_it_lost_rather_than_failing`** — deterministic, and the one that actually gates this. It holds a write lock on a default-journal store and releases it after 250ms. Before this change the open failed in **0.01s** with `database is locked`; now it takes **0.27s** and the store ends up in WAL.

## Docs

The spike README is corrected in place with the measurements above — it is an evidence document, and leaving a measured-wrong conclusion in it is how the implementation got here. ADR-018 carries a dated correction pointing at it.
