## The engine

`adapter/engine/sqlite.rs` — WAL-mode SQLite with `synchronous=FULL`:

- **Readers never block the writer, and a second writer waits for the commit lock instead of being refused.** That is the property redb does not have and the reason this exists.
- One SQL table per seam table. Text keys are `WITHOUT ROWID`, clustered on the key columns, so an ordered scan is an index walk and the adjacency query is a primary-key range. The `u64` log is `INTEGER PRIMARY KEY`.
- Ordering matches the seam contract with no collation work: `BINARY` compares bytewise, which is what `str` ordering is.
- `busy_timeout` is armed **before** `journal_mode=WAL`. Switching journal mode takes a brief lock two processes can collide on; the concurrency spike crashed exactly this way and it is now a comment in the code.
- `BEGIN IMMEDIATE` for writes — takes the write lock up front rather than upgrading later, which is the classic deadlock.
- A small per-engine connection pool so concurrent tasks inside one process each get their own snapshot.

## The layout is the gate

A SQLite store stamps **`FORMAT_VERSION = 2`**. Not because the logical event format changed — it did not; bundles from either engine are byte-identical — but because the version number is the *only* thing a binary that predates this decision honours.

Concretely: a 0.1.x binary opening a SQLite directory would read `1`, look for `store/kernel.redb`, not find it, and **create an empty one beside the real store**. Silent empty memory — the exact failure ADR-012 exists to prevent. With `2` it stops with "newer than this binary supports; upgrade the binary", which is the truth.

So `FORMAT_VERSION` names the layout, `EVENT_FORMAT_VERSION` (new constant, value 1) is what bundles carry, and the two are no longer the same number wearing two hats. A store is never reopened as another engine's — refused by name in both directions. A binary built without the feature recognises `2` and says which feature to enable.

## What is deferred, and why

**Migration from a SQLite source** is refused with the reason. WAL keeps committed data in a sidecar until checkpointed, so "copy the store file and read the copy" — what the redb migration does — would silently drop the newest events. A consistent snapshot (`VACUUM INTO`) is its own piece of work and belongs with the conversion tooling in step 3. Better to refuse than migrate incompletely.

**Engine selection** — `KMP_MCP_ENGINE`, `kmp-mcp --version` reporting layouts, redb→SQLite conversion — is step 3. This PR gives `EmbeddedKernelStore::open_with_engine` and stamps the directory; nothing in `kmp-mcp` picks SQLite yet.
