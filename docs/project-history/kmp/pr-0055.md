## Author's change description

Addresses #30 — the journey half of it. See the last section for what it does **not** fix.

## The race, in one line

The fixture's readiness probe waits for this:

```rust
&& bundle.bundles.first().is_some_and(|role_bundle| {
    !role_bundle.neighbor_nodes.is_empty()
```

Any neighbour. That is the right gate for *"the projection is alive"* and the wrong one for *"the projection has caught up"*.

The test then asserts an exact count — 17 — against a query the probe never makes: different role, different depth, a 65536 budget instead of 1200. So it was racing from its first assertion, and under `cargo-llvm-cov` everything is slower and the window widens, which is why the coverage job saw it first.

The failure shape said as much: **15 of 17, everything else correct**. Not a timeout, not a connection refused, not an empty result. Two nodes missing from an otherwise correct bundle is a read arriving early.

## The fix

`wait_for_neighbor_count` polls the query the test is about to assert until it holds what the test expects, or a deadline passes.

The assertions stay exact — this changes when they run, not what they check. A genuine regression still fails, at the deadline instead of instantly, and it says what it saw:

```
projection did not converge: expected 17 neighbours, last saw 15
```

which is a better failure than the one it replaces, because that message distinguishes "the projection is slow" from "the projection is wrong" without a re-run.

## What this does not fix

The issue also reports `integration-conformance` failing on `main` at a merge that changed **three markdown files** — good evidence that something else races too.

I went looking and did not find it. That suite has no exact-count assertion of this shape; it delegates to the conformance scenarios, and nothing there matched the pattern. So this PR fixes the journey test and leaves the conformance half of #30 open rather than closing an issue on a fix that only covers part of it.
