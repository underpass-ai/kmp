## Author's change description

Step 3 of 3 for [ADR-018](https://github.com/underpass-ai/kmp/blob/4d05bc5ec4189ee8f7f71b6e0ca42edcb8aa65bb/docs/adr/ADR-018-multi-process-embedded-store.md), the last one. After #18 (seam), #19 (engine) and #20 (migration), this is the user-facing surface: everything someone needs to put two agent hosts on one memory, from the binary they run.

## `KMP_MCP_ENGINE`

Says what a **fresh** data directory becomes: `redb` (default) or `sqlite`. An existing directory always opens with the engine it was created with.

The one design call worth a look: **asking for a different engine than the directory has is refused, not warned-and-ignored.** Opening the wrong engine behind a user's back is exactly the silent divergence that ends in "why can't my second host open it". The refusal names the fix:

```
embedded store at `…/sel2` is a redb store (format version 1), not sqlite; a store is never
reopened with another engine — to change engines, migrate it: `kmp-mcp migrate <this-dir>
<new-dir> --engine sqlite`, or unset the engine to open it as it is
```

An unknown value says which two are accepted. A default build asked for `sqlite` is refused with the feature to enable — and stamps nothing.

## What the user sees

| Surface | Before | After |
|---|---|---|
| startup line | `using embedded backend (kernel in-process)` | `… (kernel in-process, sqlite engine)` |
| `kmp-mcp --version` | `kmp-mcp 0.1.3 (store format 1)` | `… (store formats 1, 2 (sqlite))` on a build that carries it |
| `/kmp:doctor`, sqlite store held by another process | n/a | `ok  another process has this store open (pid …) — sqlite shares it` |
| `/kmp:doctor`, redb store held by another process | single-writer warning | same warning, now ending in `kmp-mcp migrate <your-dir> <new-dir> --engine sqlite` with the real path filled in |
| after a store refuses to open | `set KMP_KERNEL_GRPC_ENDPOINT for live gRPC…` | that hint only follows a backend-selection failure — the only thing it fixes |

The kernel's ADR-011 lock hint now triggers on redb's own lock text rather than any "could not open", so a SQLite open failure (permissions, say) does not get advice about a lock that engine does not take.

## Docs

`docs/operations/mcp-stdio.md` gains **Sharing one memory between two agent hosts**: install with `--features sqlite`, `KMP_MCP_ENGINE=sqlite` for a fresh store or `migrate --engine sqlite` for an existing one, point both hosts at it, and what it costs (~5× slower point reads, ~30 % slower batched writes, a C dependency; 2.5× smaller stores). It says plainly that the crates.io binary and the plugin bundles are default builds without the engine.

README, `embedded-hosts.md` and the plugin README stop describing single-writer as universal.

## Verified by hand

- fresh dir + `KMP_MCP_ENGINE=sqlite` → `FORMAT_VERSION` 2, `kernel.sqlite3`, banner names the engine
- same on an existing redb dir → refused by name with the migrate command
- default build + `KMP_MCP_ENGINE=sqlite` → refused with `--features sqlite`, only `logs/` created
- `KMP_MCP_ENGINE=postgres` → `unknown storage engine`, names the two choices
- `--version` differs between the two builds
- doctor over a held sqlite store vs a held redb store, output above
