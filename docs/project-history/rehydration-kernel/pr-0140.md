## Author's change description

## The observation

Every PR here gets **two** CodeQL workflow runs, not one. Both come from GitHub's code-scanning default setup (`dynamic/github-code-scanning/codeql`, same `workflow_id`, dispatched in the same second) — one is the security analysis (`actions`, `python`, `rust`), the other is the code-quality analysis (`python` only). So `Analyze (python)` already arrives twice on the same commit.

## The bug it exposes

`wait-codeql-checks` built its state as a `Map` keyed by check-run **name**:

```js
const states = new Map(
  checkRuns.map((run) => [run.name, { status: run.status, conclusion: run.conclusion }]),
);
```

Duplicate names collapse, and whichever run the API happens to return last silently wins. It is benign today only by coincidence: the names the gate inspects (`Analyze (actions)`, `Analyze (rust)`, `CodeQL`) are currently emitted by the security run alone. If the code-quality configuration ever covers rust or actions — plausible in a Rust repo, and outside our control since default setup is managed by GitHub — there would be two `Analyze (rust)` checks, and **a failing security analysis could hide behind a passing namesake while the gate reported success**.

## The fix

Keep every run under a required name instead of collapsing to one:

- pending if **any** run with that name is incomplete;
- failed if **any** run concluded other than success;
- failure messages disambiguate with the check-run id (`Analyze (rust)#6=failure`) when a name maps to more than one run;
- the listing is paginated instead of reading a single page.

Note this is deliberately *robust* rather than *strict*: rejecting any ambiguous name outright would fail every PR today, since `Analyze (python)` is already duplicated.
