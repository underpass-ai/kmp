## Author's change description

## What

`rehydration-memory-api` grows the write side: **`MemoryRecordApi`**, a separate trait from `MemoryRecallApi` on purpose — the recall trait keeps its reads-only promise (ADR-015's wording survives intact), and a consumer that writes declares it in its bounds. Plain specs in (`MemoryRecordRequest`: dimensions, entries, evidence, provenance), `RecordedMemoryView` out. Capability name: `record`. `CONTRACT_VERSION` stays 1 — capabilities added, no meaning moved.

## The part that needed a kernel fix

The contract promises **replay idempotence**: same `idempotency_key` + same content → the recorded outcome; same key + different content → `Refused`. The kernel could not keep that promise: the idempotency comparison hashed the *translated* changes, and translation consults existing state (a dimension already declared is not re-created), so the same logical ingest translated differently after its own first apply — **every replay read as a conflict**.

Fix: `ContextUpdatedEvent` and `IdempotentOutcome` carry a **logical digest** computed from the untranslated command (about + memory + provenance), and when both sides hold one, that is the comparison. Backward compatible by construction: serde defaults read old records as digest-less, and those keep the old strict changes-hash comparison — stricter, never looser. The Valkey adapter's `rev:hash` value format grows an optional third segment, with a test proving old values parse as digest-less.

On the record path, `PortError::Conflict` maps to `ApiError::Refused` (non-transient): a reused key with different content will not succeed by being retried, and telling a consumer to wait would have it retry a contradiction forever. The recall path keeps its ports-as-environment mapping.

## Conformance

`ingest_idempotency_replay_is_safe_and_conflicts_fail` asserted "same-key retry after success must be rejected explicitly" — that was the deficiency wearing a test's clothes. It now asserts the replay: apply twice, store once, same `memory_id`, memory unchanged; conflicting content still rejected.

## Why now

The first real consumer pipeline (an embedding product applying its durable outbox into the kernel) needs a published write surface or it keeps deep-importing `rehydration-application` types. ADR-016 records the decision.
