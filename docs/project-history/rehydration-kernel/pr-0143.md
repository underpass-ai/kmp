## Author's change description

## El problema que resuelve

La PR agrupada de dependabot **#142** sube `opentelemetry_sdk` 0.31 → 0.32 pero deja `opentelemetry-otlp` atrás, y la compilación se cae en los límites de trait:

```
error[E0277]: the trait bound `opentelemetry_otlp::MetricExporter:
              opentelemetry_sdk::metrics::exporter::PushMetricExporter` is not satisfied
error[E0277]: the trait bound `opentelemetry_otlp::SpanExporter:
              opentelemetry_sdk::trace::SpanExporter` is not satisfied
error[E0599]: no method named `tracer` found for reference `&SdkTracerProvider`
```

`PushMetricExporter`, `SpanExporter` y `MeterProvider` los define el SDK, así que un exporter compilado contra 0.31 deja de satisfacerlos. **No es una rotura de nuestro código: es desalineación dentro de una misma familia.**

## Qué hace

Mueve los cinco crates a la vez:

| Crate | Antes | Ahora |
| --- | --- | --- |
| `opentelemetry` | 0.31.0 | **0.32.0** |
| `opentelemetry_sdk` | 0.31.0 | **0.32.1** |
| `opentelemetry-otlp` | 0.31.1 | **0.32.0** |
| `opentelemetry-proto` (transitivo) | 0.31.0 | **0.32.0** |
| `tracing-opentelemetry` | 0.32.1 | **0.33.0** |

Las versiones se consultaron una a una en crates.io, no se dedujeron. Conviene fijarse en que **no avanzan en bloque**: el SDK va por 0.32.1 mientras el resto está en 0.32.0, y `tracing-opentelemetry` va una menor por delante de toda la familia (0.33.0). Precisamente por eso subir uno solo es inseguro, y por eso este movimiento no puede dejarse a un bump automático por crate.

## Coste en código: cero

Con la familia alineada, **no hace falta tocar una sola línea de fuente**. Los cinco sitios que usan la API — `rehydration-observability` (`lib.rs`, `metrics.rs`), `rehydration-mcp`, `rehydration-adapter-nats`, `rehydration-server` y `rehydration-transport-grpc` — compilan tal cual.
